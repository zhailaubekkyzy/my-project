# SmartFlow — устройство приложения и план подключений

Этот файл — карта: что уже работает на настоящих данных и куда что подключать дальше.
Подробная логика продукта — в документе «Smartflow — структура приложения».

## Нижнее меню (слева направо)

| Место | Вкладка | Сейчас | Файл |
|---|---|---|---|
| 1 | Инкубатор | Место зарезервировано, помечено «скоро» | будет `js/screens/incubator.js` |
| 2 | Маркетплейс (+ Офис) | Витрина, карточка, «Купить», Офис | `js/screens/marketplace.js`, `js/screens/office.js` |

## Как устроен фронтенд

```
index.html
 ├ js/api-client.js      связь с сервером (Railway)
 ├ js/store.js           состояние; навигация (стек экранов в каждой вкладке); кэш данных сервера
 ├ js/icons.js           иконки (собирается: npm run build)
 ├ js/ui.js              общие детали: аватар, метка SI, уведомления Бадди, процент доверия
 ├ js/data.js            загрузка настоящих данных с сервера, обновление открытого чата
 ├ js/media.js           фото: выбор на телефоне → квадрат 512×512 → JPEG → загрузка
 ├ js/screens/*.js       экраны вкладок, каждый регистрируется в window.SF.screens
 └ js/app.js             каркас: нижнее меню, переходы, кнопка «Назад» Telegram, вход, ссылки
```

- Переходы: `SF.go('chats')` — вкладка, `SF.push('consultant', { id })` — экран глубже, `SF.back()` — назад.
- Всё, что вводят люди, выводится через `SF.esc()` (защита от вставки чужого кода).
- Выдуманных данных в приложении нет: всё про SI-продавцов, чаты и клиентов приходит с сервера.

## Как отвечает SI

`server/services/si-engine.js` → OpenAI (ключ `OPENAI_API_KEY` или `OPEN_API_KEY` в Railway,
модель — `OPENAI_MODEL`, по умолчанию `gpt-4o-mini`). SI знает только карточку и методологию
SI-продавца, не выдумывает цены и факты, честно говорит, что он SI. Без ключа или при сбое
OpenAI — честный ответ «нажмите «Связаться с человеком»». Проверка: `/api/health` → `openai.configured`.

- SI пишет как живой, тёплый SI-продавец: коротко, с участием, никогда не грубит и не торопит. Сам себя ботом
  не называет, но на прямой вопрос честно отвечает, что он SI-помощник эксперта. В интерфейсе SI отмечен
  только мягко: красная точка на аватарке и красноватый оттенок сообщений.
- Человек открыл ссылку SI-продавца — SI пишет первым (приветствие, чем поможет, один вопрос): `POST /api/chat/:slug/start`.
- Лимит ответов SI на клиента — из методологии SI-продавца.
- **SI-мозг** (`server/services/brain-service.js`, `/api/brain/materials`, Офис → «SI-мозг»): эксперт загружает
  PDF, Word (.docx) или текст до 10 МБ. Сервер достаёт текст, режет на части по ~1200 знаков и для каждой
  получает у OpenAI «смысл» (embedding `text-embedding-3-small`, 512 чисел). Сам файл не сохраняется.
  На вопрос клиента SI получает 5 самых подходящих частей только тех материалов, что открыты этому SI
  (если у SI меньше 6000 знаков материалов — все целиком). Без OpenAI поиск идёт по словам; части без
  «смысла» досчитываются позже сами. Лимиты: 50 материалов, 400 тыс. знаков в одном, 2 млн знаков всего.
- «Связаться с человеком» → SI для клиента на паузе, эксперту пишет бот с кнопкой «Открыть обращение».
- Эксперт ответил лично → клиенту пишет бот с кнопкой «Открыть чат». Эксперт может включить SI обратно.
- Бот может писать человеку, только если тот разрешил: приложение просит разрешение при открытии Офиса,
  при «Связаться с человеком» и по кнопке «Уведомления в Telegram → Включить» в Профиле.

## Бизнес и помощник

`server/services/business-service.js`, `/api/business`, Офис → «Помощник».
- **Бизнес** — компания эксперта над SI-продавцами: SI-продавцы, клиенты, переписки и «Мне написали»
  принадлежат ему (`business_id`). Появляется, когда эксперт включил SI-продавца: принял условия Офиса,
  создал SI-продавца или с его SI-продавцом начал переписываться клиент. Один бизнес на эксперта.
- **Участники** — строки `business_members` (роль `owner` / `assistant`). Помощник один: `MAX_ASSISTANTS = 1`
  в `business-service.js` (поднять лимит — поменять цифру). Владелец приглашает по номеру `SF-…`, бот
  сообщает помощнику. Убрать помощника может только владелец; его диалоги возвращаются владельцу.
- **Права проверяет сервер** (`project-service.checkProjectAccess`): помощнику — только `conversations:read/write`
  (клиенты, «Мне написали», ответ, пауза/запуск SI). Без денег (`payment_url`, цена, `deal_value`), SI-мозга,
  настроек SI-продавцов и аналитики. RLS в Supabase остаётся закрытым замком.
- **Автор сообщения**: `conversations.author_type` (`si` / `client` / `owner` / `assistant`) + `author_user_id`.
  Старое поле `sender` сохранено для совместимости.
- **Ответственный за диалог**: `clients.responsible_type` (`si` / `human`) + `responsible_user_id`.
  Пауза SI = ответственный человек. «Связаться с человеком» → ответственный владелец; ответил помощник →
  ответственный помощник; «Включить SI» → снова SI. Старый `status = 'human_needed'` больше не используется.

## Журнал событий и воронка

`server/services/funnel-service.js`, `/api/business/funnel`, Офис → «Воронка» (владелец и помощник).
- **Журнал** `client_events` — строка на каждое действие клиента или человека. Карточка клиента в Офисе
  показывает статус, последнее возражение, кнопки «✓ Купил» / «Отказ» / «Вернуть в воронку» и журнал.
- **5 статусов** (названия владелицы): «Ждут человека» (яркий), «Есть возражения», «Не дошли до конца воронки»,
  «Купили» (зелёный), «Отказ» (серый). Ключи в базе: `waiting_human`, `objections`, `not_finished`, `bought`, `refused`.
  «Есть возражения» = клиент ответил на оффер или засомневался, но не купил. «Купили» и «Отказ» — отмечают
  люди (оплата идёт мимо платформы); отказ SI тоже замечает сам.
- **Как SI замечает события**: вместе с ответом SI идёт второй короткий запрос к OpenAI (`si-engine.analyzeTurn`,
  JSON): был ли в прошлом сообщении оффер, ответил ли клиент на него, возражение (2–5 слов), отказ. Ответ
  клиенту не ждёт этот разбор дольше, чем сам ответ; сбой разбора не ломает чат. Без ключа OpenAI автоматических
  событий нет (остаются «написал», «Купить», ручные отметки). «Оффер» отмечается, когда клиент ответил после него.
- **Кнопка «Купить»** в чате клиента пишет событие `buy_clicked` (`POST /api/chat/:slug/events`).
- **Экран «Воронка»**: фильтр 7 / 30 дней / всё время (по последней активности), подсчёт по запросу,
  списки по 30 с «Показать ещё».
- **Ветки «если…, то…»** (сценарии) — внутри методологии SI-продавца (Офис → SI-продавец → «Карточка и методология»).
  Воронка — дерево веток (решение владелицы): инструмент, которым эксперт или маркетолог строит любые ветки сам.
  В начале блока — **«Общее описание»** методологии (`custom_ai_settings.methodology`, до 3000 знаков): своими словами,
  как SI ведёт клиента к покупке; SI следует ему в каждом разговоре. Ниже — отдельные сценарии.
  **Готовых условий нет — эксперт пишет условие словами** (решение владелицы). Форма: «Когда срабатывает» —
  «Клиент написал или сделал то, что я опишу» (условие словами) или «Клиент молчит» (минуты + после чего: в любой
  момент / опишу словами / после другого сценария). Условия словами SI проверяет и по нажатым кнопкам («Купить»,
  «Отправить чек», «Поделиться контактом»). Без ключа OpenAI работают слова в кавычках («рассрочка»).
  Старые типы условий (возражение, оффер…) сервер ещё понимает, но в форме их больше нет.
  У ветки может быть название («Хочет рассрочку»). Действие **«Отправить клиенту мой текст или ссылку»** — материал
  как есть (например, «ответил так → материал A, ответил вот так → материал B»; один раз на клиента). «Клиент замолчал»
  может идти **после другой ветки** («после ветки «Новичок» молчит 60 минут → …») — так ветки связываются в дерево;
  при удалении ветки удаляются и идущие после неё.
  По умолчанию сценариев нет: у каждого SI-продавца свои, эксперт пишет их сам (до 20).
  Если: клиент возразил (можно указать слова: «дорого, нет денег»), ответил на оффер, нажал «Купить», прислал чек,
  отказался, или **своё условие словами** («клиент спрашивает про рассрочку» — его замечает тот же разбор переписки).
  То: «SI отвечает так: …» (уходит в инструкции SI), «передать человеку» (SI на паузу + «Мне написали»),
  «сообщить мне в SmartFlow» (владельцу и помощнику). Действия срабатывают один раз на клиента. До 20 сценариев.
  Сценарии «через время» (клиент замолчал) — после «будильника» на сервере.
- **Кнопки «Отправить чек» и «Поделиться контактом» скрыты по умолчанию** (не пугать клиента): сервер
  (`chat-service.chatTools`, поле `tools` в `/api/chat/:slug/messages`) показывает «Отправить чек» после «Купить»
  или когда SI/человек в последних 3 сообщениях говорит об оплате или чеке (до покупки), «Поделиться контактом» —
  когда SI/человек попросил номер (пока клиент не поделился). SI просит номер, только когда он правда нужен.
- **Контакт клиента** — как в Telegram: в чате кнопка «Поделиться контактом» открывает родное окно Telegram
  (`WebApp.requestContact`). Ответ подписан Telegram; сервер проверяет подпись и что это контакт самого человека,
  затем сохраняет `clients.contact_phone` и момент согласия `contact_consent_at`. Номер видят владелец и помощник.
- **Чек об оплате** (`server/services/receipt-service.js`, таблица `payment_receipts`): в чате кнопка «Отправить чек»
  (фото или PDF до 5 МБ; фото сжимается на телефоне до 1600 px). Чек виден только клиенту и людям бизнеса
  (не через публичные `/api/media`). Клиент → «Ждут человека», обращение в «Мне написали», бот пишет владельцу и помощнику.
  В карточке клиента: «Подтвердить оплату» → «Купили» и сообщение клиенту; если у SI-продавца задана
  «Ссылка на доступ после оплаты» (`projects.access_url`), она уходит клиенту **только после подтверждения человеком**.
  SI эту ссылку не знает, сам оплату не подтверждает и просит прислать чек. «Не подтверждаю» — мягкое сообщение клиенту.

## Шаги воронки SI-продавца

`server/services/funnel-service.js` (шаги), `chat-service.moveToStep`, Офис → SI-продавец → «Карточка и методология» → «Шаги воронки»;
Офис → «Воронка» → «По шагам». Миграция 014.
- **Шаги** (`custom_ai_settings.steps`, до 8, по умолчанию нет): путь клиента к покупке, например знакомство → материал
  → вопросы и возражения → встреча или оффер → оплата. У шага: название, что SI делает на шаге, «шаг пройден, когда…»
  (словами) и материал (текст или ссылка, необязательно). Порядок меняется стрелками.
- **Шаг клиента** — `clients.step_id` (пусто или удалённый шаг = первый шаг) и `step_at`. SI получает в инструкции весь путь
  и шаг этого клиента («веди мягко к следующему, шаги не называй»). Старое поле `funnel_step` не используется.
- **Переход дальше**: тот же разбор переписки (`si-engine.analyzeTurn`, поле `steps_done`) решает, пройден ли шаг; кнопки
  («Купить», чек, контакт) проверяются так же. SI переводит **только вперёд** (можно через шаг), купивших и отказавшихся
  не двигает. Без ключа OpenAI срабатывают слова в кавычках из «пройден, когда» («готов»). Владелец или помощник может
  перевести клиента на любой шаг вручную в карточке клиента (`POST …/clients/:id/step`). Каждый переход — событие
  `step_reached` в журнале.
- **Материал шага** приходит клиенту от SI один раз, когда SI перевёл его на шаг (материал первого шага — сразу после
  приветствия). При ручном переводе материал не отправляется — чтобы клиенту ничего не пришло неожиданно.
- **Сценарии и шаги**: условие «Клиент перешёл на шаг …» (действия: материал, передать человеку, сообщить мне) и для
  остальных сценариев поле «Шаг воронки» — сценарий работает, только пока клиент на этом шаге (в том числе «Клиент молчит»).
  Удалили шаг — удаляются и его сценарии.
- **«По шагам»** (`GET /api/business/funnel/steps?projectId=&days=&step=`, владелец и помощник; помощник видит только
  названия шагов): по каждому шагу «дошли» (на шаге или дальше, % от предыдущего), «сейчас здесь», «отказ», отметка
  «здесь чаще останавливаются» (больше всего «сейчас здесь» + «отказ»); нажатие на шаг — список клиентов по 30.

## Отзывы реальных клиентов

`server/services/review-service.js`, миграция 016. Решения владелицы 15 окт.:
- Отзыв оставляет **только клиент с отметкой «Купили»** (её ставят вы или помощник), **один на SI-продавца**, его можно
  изменить. Оценка 1–5 и текст до 1000 знаков. В чате с SI-продавцом после покупки — тихая строка «Поделитесь
  впечатлением — оставьте отзыв» (потом «Ваш отзыв ★★★★★ · Изменить»).
- Все видят **только имя и первую букву фамилии** («Анна К.»), без профиля и номера. Карточка в Маркетплейсе: средняя
  оценка, число, отзывы с ответами автора; в списке — «★ 4,5 (2)». Выдуманных отзывов нет.

## Рассылки SI-продавца

`server/services/broadcast-service.js`, `/api/projects/:id/broadcasts`, Офис → SI-продавец → «Рассылки», миграция 017.
Анонсы: мероприятие, новость, акция (решения владелицы: словами, только после подтверждения, помощник — с одобрения).
- Эксперт пишет словами «кому и что» → SI (OpenAI, JSON) выбирает аудиторию и пишет текст; без ключа — форма вручную.
  Аудитория: статусы воронки (кроме «Отказ»), шаги воронки, «писали за 7/30/90 дней», слово из возражения. Перед
  отправкой видно «Получат: N · имена» и текст можно поправить.
- Владелец отправляет сразу или сохраняет черновик; **помощник — только «на одобрение»**: владельцу приходит сообщение,
  он нажимает «Одобрить и отправить» или «Отклонить».
- Куда приходит: **в чат клиента с SI-продавцом** — сообщение от эксперта с пометкой «📣 Рассылка» (`conversations.is_broadcast`,
  SI не встаёт на паузу), плюс уведомление у Бадди / в Telegram с кнопкой в чат. В журнале клиента — «Получил рассылку».
- Правила против спама: только писавшим хоть раз; никогда — отказавшимся и нажавшим «Не присылать рассылки»
  (`clients.broadcasts_off_at`, кнопка под рассылкой в чате, можно включить обратно); **1 рассылка в день и 3 в неделю**
  на SI-продавца; отправляет «будильник» (`broadcasts`) порциями до 100 в минуту, **только 9:00–21:00 по времени
  клиента** (часовой пояс с телефона; неизвестен — `DEFAULT_TZ_OFFSET_MINUTES`, по умолчанию Алматы +300).
  Получатели фиксируются в момент запуска (`broadcast_recipients`); остановить можно на ходу.
- По окончании владельцу (и помощнику, если готовил он) — «Рассылка отправлена: получили N из M».
- Те же тихие часы теперь и у «Клиент замолчал»: SI-сообщения и материалы ночью ждут утра клиента.

## Ссылки с меткой источника, приглашения и партнёры

`server/services/partner-service.js`, миграция 020. Решения владелицы 15 окт.
- **Ссылки с меткой источника (UTM)**: Офис → SI-продавец → «Ссылки с меткой источника», **до 3 на SI-продавца**. Эксперт

  конце сама. Рядом со ссылкой две кнопки: **«Отправить»** — системное окно телефона «поделиться» (`navigator.share`:
  WhatsApp, Instagram, Telegram и любые приложения; где его нет — текст копируется) и **«Скопировать»**. Приглашённый
  попадает к своему Бадди, и Бадди первым пишет: «Вас пригласил(а) …», чем поможет и с чего начать (на его языке).

  SI-продавцы партнёра — **в верхних строках Маркетплейса** (`listConsultants`: сначала партнёры) и с прибавкой +15 к
  оценке в альтернативном оффере (`PARTNER_BONUS`); **+10 сообщений Бадди в день за каждого пришедшего** (лимит = 30 +
  10 × пришло, `buddy-service.dailyLimit`). Про процент в будущем на карточке не пишем (решение владелицы).

  к чужому SI-продавцу, не считается нигде. **Новый человек** (первый вход в SmartFlow) навсегда засчитывается ссылке,
  по которой пришёл (`users.referred_by_link`). **Клиент SI-продавца** — первой ссылке этого SI-продавца, которую человек

  В Профиле и в публичном профиле — крупная медаль с числом пришедших (`SF.partnerMedal`).
- Панель поддержки → «Партнёры»: кто приводит людей (лучшие сверху), куда ведут его ссылки и сколько с каждой пришло,
  стали клиентами, купили. PostHog: `link_opened`.

## Альтернативный оффер над чатом

`server/services/alt-offer-service.js`, миграция 019. Решение владелицы 15 окт.: «наша задача — решить проблему
конечного потребителя и скорее найти ему решение».
- Когда SI заметил **возражение** клиента в чате эксперта А, над чатом появляется полоса «Может подойти и это» —
  **до 3 SI-продавцов других экспертов** из Маркетплейса. Участвуют **все** показанные в Маркетплейсе (активные, с оффером),
  **в том числе из той же ниши**; кроме SI-продавцов самого эксперта А. Нажатие открывает карточку; полосу можно закрыть.
- **Кого выше**: оценка проработанности 0–100 (`qualityScore`): общее описание методологии, сценарии, закрывающие
  возражения, шаги воронки, описание продукта, цена и ссылка на оплату, реальные отзывы, SI-мозг. Из 15 лучших SI

  В Офисе эксперту подсказка: чем подробнее методология, тем чаще его SI-продавец появляется у клиентов других экспертов.
- Подборка хранится у клиента (`clients.alt_offers`, `alt_offers_at`), видна 7 дней; после «Купили» у эксперта А — нет.

- В журнал клиента эксперта А ничего не пишется; цифры — PostHog (`alt_offers_shown`, `alt_offer_opened`).

## «Будильник» на сервере

`server/services/scheduler-service.js`: раз в минуту сервер запускает свои задачи. Таблица `scheduler_jobs` —
строка на задачу: «замок» (`locked_until`), чтобы две копии сервера (например, во время обновления на Railway)
не выполняли одно и то же дважды, время и итог последнего запуска, последняя ошибка. Ошибка одной задачи
не останавливает сервер и повторяется через минуту. Состояние: `/api/health` → `scheduler`, панель поддержки →
«Состояние системы» (ошибки — в «Требует внимания»).

Задачи сейчас:
- **`silent-clients`** (`server/services/followup-service.js`) — догоняющие сообщения как сценарии «если…, то…»
  **в методологии** SI-продавца (решение владелицы: воронка — дерево, догоняющее зависит от ветки и контекста).
  Условие «Клиент замолчал на N минут» (5 минут – 30 дней, от последнего сообщения клиента) + после чего: в любой
  момент / после оффера / после возражения / после «Купить», но без чека / после другой ветки. Действия: «SI
  отвечает так» (SI сам пишет короткое тёплое сообщение; подсказка необязательна), «отправить мой текст или
  ссылку» (клиенту — уведомление бота), «передать человеку», «сообщить мне в SmartFlow». По умолчанию веток нет.
  - «После оффера»: последнее сообщение SI проверяется один раз (OpenAI, без ключа — по словам «Купить»,
    цене, офферу); найденный оффер записывается в журнал (`offer_sent`).
  - Правила платформы против спама: только если последнее сообщение не от клиента и клиент хоть раз писал сам;
    купившим и отказавшимся — никогда; пока клиенту отвечает человек, SI молчит; каждый сценарий — один раз,
    пока клиент снова не напишет; одно действие на клиента в минуту; за одно молчание не больше 3 сообщений SI
    с паузами между ними; диалоги, молчащие дольше самого долгого сценария + 3 дня, не будятся; не больше 50
    действий в минуту на всю платформу.
- **Рассылки** — отдельно: раздел «Рассылки SI-продавца» (задача `broadcasts`).
- Напоминания о встречах — задача `meeting-reminders` (раздел «Календарь»). Дальше: вебинары.

Часовой пояс клиента берётся с телефона (`users.tz_offset_minutes`: Бадди, запись на встречу). Сообщения клиенту по
«Клиент замолчал» и рассылки уходят только 9:00–21:00 по его времени (неизвестен — Алматы).

## Бадди — переписка (личный помощник)

`server/services/buddy-service.js`, `/api/buddy/*`, `js/screens/buddy.js`. Решения владелицы: главный экран — чат с
Бадди; Бадди — личный помощник на каждый день (планы, дела, напоминания, позже календарь); готовых окошек-разделов
нет — кнопка в раздел только под сообщением, когда нужно; уведомления — сообщения Бадди; лимит 30 сообщений в день.
- Переписка хранится в `notifications` (`sender` = `buddy` / `user`, `kind` = `notice` / `chat`, миграция 010).
- Ответ Бадди — OpenAI (`BUDDY_MODEL` в Railway, по умолчанию как `OPENAI_MODEL`), JSON: текст, новые напоминания
  («ГГГГ-ММ-ДД ЧЧ:ММ» по часам человека), отмена напоминаний по номеру, кнопка в раздел (`GO_marketplace`,
  `GO_office`, `GO_chats`, `GO_profile`, `S_support`). Бадди знает имя, текущее время человека и его напоминания;
  ничего не продаёт; на прямой вопрос — честно SI.
- Часовой пояс — с телефона (`users.tz_offset_minutes`, минуты к востоку от UTC).
- Напоминания — `buddy_reminders`; «будильник» (`buddy-reminders`) в нужную минуту присылает «⏰ Напоминаю: …»
  сообщением Бадди и в Telegram, один раз.
- Лимит: 30 сообщений человека в день + 10 за каждого, кто пришёл по его ссылкам (с полуночи по его времени); после — одно мягкое сообщение, OpenAI не зовётся.
  Напоминания и уведомления не ограничены. Без ключа OpenAI — честный ответ, что Бадди пока не отвечает.
- Открытый экран Бадди отмечает всё прочитанным (красная точка на кнопке гаснет), новые сообщения подгружаются сами.
- **Календарь «для всей жизни»** (решение владелицы 15 окт., миграция 015). Над перепиской — полоса: слева «Месяц»
  (весь месяц, точка — в этот день что-то есть, нажатие на день — его планы), справа «Сегодня / Завтра / дата
  послезавтра»; под ними только ближайший план и следующий со временем («13:00 Созвон с коучем»); если планов больше —
  конец мягко затухает, нажатие показывает весь день. Сегодня — только то, что ещё впереди.
  - Планы человек говорит Бадди словами или голосом; Бадди отвечает JSON `plans: [{text, at, remind_before}]`
    (старый формат `reminders` тоже понимает). План — строка `buddy_reminders` (`kind = 'plan'`, `starts_at` — когда
    будет); **напоминание — только если человек попросил** (`notify`, `remind_at` = `starts_at` − `remind_before`):
    «⏰ Скоро, в 18:00: Ужин с Айнур». Перенос = отмена + новый план. Убрать план можно и кнопкой в списке дня.
  - Встречи с экспертами (`meetings`) видны в календаре сами: у клиента — «Встреча: «SI-продавец»», у эксперта и
    помощника — «Встреча с клиентом»; Бадди знает их и отвечает на «что у меня завтра?», но меняют их в чате или Офисе.
  - `GET /api/buddy/calendar?from=&to=` (до 62 дней), `DELETE /api/buddy/plans/:id` — только свои.
- **Голосовые Бадди** (`POST /api/buddy/voice`): до 1,5 минуты, расшифровка OpenAI, Бадди отвечает на текст;
  сама запись не хранится (в переписке — текст с микрофоном). Входит в лимит 30 сообщений в день.
- Поле ввода внизу экрана, сразу над меню (переписка занимает всё место между календарём и полем).

## Голосовые сообщения

`server/services/voice-service.js`, `POST /api/chat/:slug/voice`, `js/media.js` (`recordVoice`), `js/screens/chats.js`.
- Клиент в чате с SI-продавцом нажимает микрофон: запись до **1,5 минуты** (решение владелицы), ненавязчивый таймер
  «0:12 / 1:30», на 1:30 запись отправляется сама. Битрейт 32 кбит/с (~400 КБ за 1,5 мин).
- Проверка 13 окт. (iPad, Telegram 9.6): запись в Telegram работает, формат `audio/webm; codecs=opus`.
- Сервер проверяет файл по содержимому (webm / ogg / m4a / wav / mp3, до 3 МБ), хранит его в `voice_messages`
  (приватно: слушают только сам клиент и люди бизнеса; позже можно перенести в Supabase Storage) и просит у OpenAI
  расшифровку (`TRANSCRIBE_MODEL`, по умолчанию `whisper-1`). Текст расшифровки — это сообщение клиента: SI отвечает
  на него, возражения и сценарии работают как с текстом. В переписке — «▶ 🎤 0:18» и расшифровка под ним.
- Без ключа OpenAI или при сбое: голосовое сохраняется, SI честно просит написать текстом.
- Не больше 20 голосовых в сутки от одного клиента (расходы на расшифровку).

## Календарь (встречи с клиентами)

`server/services/calendar-service.js`, миграция 012, `/api/business/calendar*` (Офис), `/api/chat/:slug/calendar*`
(клиент), Офис → «Календарь», окошко записи в `js/screens/chats.js`. Решения владелицы:
- Свободные окна задаёт **эксперт — себе и помощнику** (дни недели + часы, несколько окон в день), у каждого своя
  постоянная ссылка Zoom и галочка «Принимает встречи». Длительность встречи: 15/30/45/60/90 мин.
- Окна — во времени бизнеса (`calendar_settings.tz_offset_minutes` = часовой пояс телефона владельца при сохранении);
  встречи хранятся в UTC; клиент видит время своего телефона, сообщения ему — тоже в его времени.
- Клиент записывается **в чате с SI-продавцом**: кнопка «Записаться» появляется, когда SI или человек заговорил о
  встрече/созвоне/консультации (или у клиента уже есть встреча — «Моя встреча»). Свободное время — на 14 дней
  вперёд, не раньше чем через час. SI знает, что запись есть, но время сам не называет.
- **Без двойной брони:** проверка пересечений (и со встречами этого человека в других бизнесах) + уникальный индекс
  в базе «один человек — одно время». Если окно есть у обоих, встречу берёт первый свободный; одновременно нажавшим
  на одно время — «уже заняли». У клиента одна предстоящая встреча.
- **Перенос и отмена:** может ли клиент сам перенести / отменить и не позже чем за сколько часов — решает эксперт
  («Правила записи»). Владелец и помощник отменяют всегда. Клиенту — сообщение в чате.
- Уведомления (Бадди, потом Telegram): новая запись, перенос, отмена — тому, кто ведёт, и владельцу; за **час до
  встречи** — обеим сторонам (`meeting-reminders`, один раз).
- Журнал: «Записался», «Перенёс встречу», «Встреча отменена» (статус воронки не меняют).
- Статусы встречи: запланирована / перенесена / отменена / состоялась / не пришёл (два последних отмечают владелец
  или помощник после начала). Пустые поля под запись, расшифровку и анализ звонка (`recording_url`, `transcript`,
  `analysis`).
- Помощник видит календарь бизнеса и встречи, отменяет и отмечает итог; окна и правила меняет только владелец.
- Дальше: календарь «для всей жизни» у Бадди; сравнить по цифрам запись у Бадди и в чате (доля записавшихся,
  доля пришедших, время до записи).

## Люди: поиск и переписка

`server/services/people-service.js`, `/api/people/*`, миграция 013 (`dm_threads`, `dm_messages`, `dm_files`,
`users.hidden_from_search`), экран `person` во вкладке «Чаты» (`js/screens/chats.js`). Решения владелицы (14 окт.):
цель — чтобы люди привыкли общаться и обмениваться в SmartFlow; в Telegram не уводим.
- **Поиск.** Маркетплейс — строка поиска SI-продавцов (название, оффер, эксперт). «Чаты» — одна строка: свои
  переписки (SI-продавцы и люди) и «Люди в SmartFlow» с сервера: по имени, @нику, строке под именем, от 2 букв, до
  20 человек, только после входа. Не находятся: скрывшиеся («Показывать меня в поиске» в Профиле, по умолчанию
  включено), заблокированные платформой, демо и те, кто заблокировал меня. Номер SF-… в поиске не участвует.
- **Переписка.** Кнопка «Написать» в профиле человека и в результатах поиска. Одна переписка на пару людей.
  Первое сообщение приходит с «Принять / Заблокировать»; ответ тоже принимает. Настроек «кто может писать» нет.
- **Защита от спама:** до ответа — не больше 3 сообщений (`PENDING_LIMIT`); не больше 20 новых знакомств в сутки
  (`NEW_PER_DAY`); «Заблокировать» / «Разблокировать» (заблокированный не может писать и не находит, ему просто
  «не доставлено»); «Пожаловаться» — жалоба в `feedback` с причиной и последними 20 сообщениями (команда видит
  личную переписку только так) и сразу блокировка.
- **Уведомления:** у Бадди, потом в Telegram, кнопка ведёт в переписку (`U_<id>`); одно на непрочитанные, а не на
  каждое сообщение. Число на кнопке «Чаты» учитывает непрочитанные и «хочет пообщаться».
- **Файлы в переписке:** голосовые до 1,5 мин, фото (телефон уменьшает до 1280 px), видео-кружки до 30 сек
  (фронтальная камера, круг как в Telegram). Хранятся в `dm_files` (позже — Supabase Storage), сервер проверяет файл
  по содержимому, отдаёт только двоим участникам (`/api/people/:userId/files/:fileId`); не больше 60 файлов в сутки.
  Запись идёт в окошке поверх экрана, чтобы новые сообщения её не прерывали. Камеру внутри Telegram на iPhone/Android
  ещё проверить (как микрофон).
- **Поиск по ключевым словам:** все слова запроса должны найтись в имени, @нике, строке под именем или «О себе».
  У найденного — две кнопки: «Профиль» и «Написать».
- **Бадди людей не рекомендует** (решение владелицы): не предлагает писать и не называет людей; может посоветовать
  SI-продавца, позже — группу в Инкубаторе.

## Уведомления: сначала Бадди, потом каналы доставки

Решение владелицы: Бадди обязателен для всех уведомлений, остальное — дублирует. `notify-service.notifyUser`
(старое имя `telegram-bot.notifyUser` ведёт туда же) сначала записывает уведомление в таблицу `notifications`
(у человека в Бадди, «Уведомления»), потом отправляет то же на телефон через каналы доставки `CHANNELS`.
Сейчас канал один — Telegram (если человек разрешил боту писать). Решение владелицы 16 окт.: не зависеть только
от Telegram — новый канал (веб-уведомления Web Push, своё приложение, почта) добавляется одной строкой в `CHANNELS`:
`{ name, send(userId, { text, buttonText, startParam }) → true, если доставлено }`. Сломанный канал не мешает другим.
У уведомления — куда оно ведёт (`start_param`, как у кнопки бота: `I_<projectId>`, `<slug>`, `S_support`…).
`/api/me/notifications` — мои последние 30 и сколько непрочитанных; `POST /api/me/notifications/read` — одно или
«Прочитать все». Каждый видит и отмечает только свои.
Сценарий «то» называется «Сообщить мне в SmartFlow» (так понятнее людям), уведомление идёт по этой же цепочке.

### Пульс: новое на любом экране

Пока приложение на экране, `js/data.js` раз в 4 секунды спрашивает `GET /api/me/pulse` — один запрос к базе:
сколько непрочитанных у Бадди и когда последний раз менялись уведомления, переписки с людьми (`dm_threads`) и мои
чаты с SI-продавцами (`clients.last_activity`). Перезагружается только изменившийся список (и открытый чат), так что
сообщение доходит за секунды, даже если человек на другой вкладке. При возвращении в приложение (`visibilitychange`,
Telegram `activated`) и при появлении сети — проверка сразу. Свёрнутое приложение не спрашивает.

### Чтобы ничего не висело

- Телефон ждёт ответа сервера до 20 с (отправка — до 90 с, материал SI-мозга — до 3 мин), потом пишет
  «Сервер долго не отвечает» с кодом ошибки.
- База: подключение до 10 с, запрос до 30 с; обрыв простаивающего соединения не останавливает сервер.
- Ответы дольше 2 с — в логах Railway (`[SmartFlow Slow]`); `/api/health` → `database.pingMs`.

## Проверка микрофона (перед голосовыми)

Панель поддержки → «Проверка микрофона» (`js/screens/admin.js`): запись до 1,5 минуты внутри Telegram на этом
устройстве, формат записи, размер, прослушивание. Ничего не загружается; «Отправить результат команде» шлёт
только текстовую сводку (устройство, версия Telegram, формат) в «Поддержку».

## Важно помнить

- Цифровые товары внутри Telegram Mini App по правилам Telegram оплачиваются через Telegram Stars.
  Пока платформа не принимает платежи, это нас не касается; при подключении — проверить заранее.
- Личные данные граждан Казахстана по закону должны храниться на серверах в РК — вопрос к юристу
  до массового запуска.
- В базе Supabase остались демо-записи первой версии (`is_demo = 1`, «Елена Воронова», «Громов»).
  В приложении они не показываются: в Маркетплейс попадают только настоящие SI-продавцы.
- RLS (закрытый публичный доступ Supabase) теперь включается в миграциях: блок
  `-- postgres-only:begin … -- postgres-only:end` выполняется только на PostgreSQL.
